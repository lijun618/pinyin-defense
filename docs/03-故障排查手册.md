# 拼音战机 · 后端故障排查手册

> 按"现象 → 原因 → 处理"组织。每一节都可独立查阅，不必从头读。
> 排查前先跑一遍第四节的三条命令，能定位 80% 的问题。

---

## 一、快速定位表

| 现象 | 最可能原因 | 跳到 |
|---|---|---|
| 前端提示"无法连接后端服务" | 后端没启动 / 端口不对 / CORS 被拦 | §2.1 |
| `curl /health` 返回 503 或 500 | 数据库连不上、库不存在 | §2.2 |
| 后端启动即报 `Access denied (1045)` | `.env` 密码或用户错 | §2.3 |
| 注册接口 500，日志有 `__about__` | bcrypt 5.x 与 passlib 不兼容 | §2.4 |
| 注册返回 422 | 请求体字段/长度不符 | §2.5 |
| 启动报 `[Errno 10048]` | 8000 端口被占用 | §2.6 |
| 保存记录返回"用户不存在" | `user_id` 不匹配 / 已清理数据 | §2.7 |
| 保存记录报 `1452` | 外键指向的 user 不存在 | §2.8 |
| 排行榜为空但库里有数据 | 关联查询没匹配上 / 字段为 NULL | §2.9 |
| 中文用户名乱码 | 连接或表字符集不是 utf8mb4 | §2.10 |
| `pip install` 报 429 | 镜像限流 | §2.11 |
| 改了代码没生效 | 没开 `--reload` 或开了多个进程 | §2.12 |

## 二、逐项排查

### 2.1 前端提示"无法连接后端服务"

**现象**：点登录/注册后红字提示"无法连接后端服务，请确认 FastAPI 已启动"；
排行榜显示同样提示。

**原因**（按概率排序）：
1. uvicorn 没启动，或启动后立刻退出了。
2. 前端 `API_BASE` 与实际监听地址/端口不一致。
3. 浏览器拦了请求（CORS 或 `file://` 的限制）。
4. 防火墙/代理拦截 localhost。

**处理**：

```bash
# ① 后端是否活着
curl -v http://127.0.0.1:8000/health
```

- 返回 `{"ok":true,...}` → 后端正常，问题在前端或浏览器，去看 DevTools。
- `Connection refused` → 后端没起来，回到终端看 uvicorn 日志。
- `curl` 正常但浏览器失败 → 按 F12 打开 DevTools → Network，点那条失败请求：
  - `CORS error`：确认 `main.py` 里 `CORSMiddleware` 已注册（本项目已开 `*`）。
    注意 `allow_origins=["*"]` **不能**和 `allow_credentials=True` 同时使用，
    否则浏览器直接拒绝。
  - `TypeError: Failed to fetch`：多为 `API_BASE` 写错（如 `https` 写成 `http`、
    端口写成 8001）。

前端地址在 HTML 顶部：

```js
const API_BASE = 'http://127.0.0.1:8000';   // 必须与 uvicorn --port 一致
```

### 2.2 `/health` 返回 503 或 500

`/health` 是专门用来验证"后端 ↔ 数据库"链路的接口：

```json
// 数据库不可用时
HTTP 503  {"detail": "数据库不可用: (2003, \"Can't connect to MySQL server on '127.0.0.1'\")"}
```

**处理顺序**：

```bash
# ① 服务在跑吗
Get-Service MySQL80          # 期望 Running
net start MySQL80

# ② 端口在听吗
netstat -ano | findstr :3306

# ③ 库和表存在吗
mysql -uroot -p -e "SHOW DATABASES LIKE 'pinyin_war_game';"
mysql -uroot -p -D pinyin_war_game -e "SHOW TABLES;"
```

- 库不存在 → 重新执行 `mysql -uroot -p < sql/init_db.sql`。
- 表不存在 → 同上（`init_db.sql` 里带 `CREATE TABLE IF NOT EXISTS`）。
- 2003 错误 → MySQL 服务未启动，或 `DB_PORT` 写成了 3307 之类。

### 2.3 `Access denied for user 'root'@'localhost' (1045)`

**原因**：`backend/.env` 里的 `DB_PASSWORD` 与实际 root 密码不一致；
或密码含特殊字符（`#`、`;`、引号）在 ini 中被截断。

**处理**：

```ini
# backend/.env
DB_PASSWORD=你的数据库密码
```

- 密码含 `#` 时不要加引号，`.env` 会把 `#` 之后当注释；含空格则用引号包起来。
- 验证凭据是否可用：

```bash
mysql -uroot -p你的密码 -e "SELECT 1;"
```

- 若确实忘了 root 密码，需走 skip-grant-tables 重置流程（见安装指南附录），
  重置后记得 `FLUSH PRIVILEGES;`。

### 2.4 注册 500，日志出现 `AttributeError: module 'bcrypt' has no attribute '__about__'`

**原因**：`bcrypt` 5.x 删除了 `__about__` 属性，而 `passlib 1.7.4` 的
`bcrypt` backend 在初始化时会读它，于是直接抛异常。

**处理**（本项目已锁定版本，这是重装环境时最常踩的坑）：

```bash
python -m pip uninstall -y bcrypt
python -m pip install bcrypt==4.0.1
python -c "import passlib, bcrypt; print(passlib.__version__, bcrypt.__version__)"
# 期望: 1.7.4 4.0.1
```

> `security.py` 里已内置一段兼容补丁（缺 `__about__` 时补一个假对象），
> 但**仍建议锁 4.0.1**：高版本 bcrypt 对超长密码的处理行为也有变化，
> 补丁只能消除报错，不能保证行为完全一致。

自检：

```bash
cd backend && python security.py
# hash: $2b$12$...
# verify ok: True
# verify bad: False
```

### 2.5 注册返回 422 Unprocessable Entity

**原因**：请求体不满足 Pydantic 模型约束。

```json
{"detail":[{"type":"too_short","loc":["body","password"],
  "msg":"String should have at least 6 characters"}]}
```

**约束表**：

| 字段 | 约束 |
|---|---|
| username | 3–32 个字符；仅允许中文、字母、数字、下划线 |
| password | 6–64 位，任意字符 |

典型报错对照：

| 输入 | 返回的 `detail[0].msg` |
|---|---|
| `小明`（2 字） | String should have at least 3 characters |
| 33 个汉字 | String should have at most 32 characters |
| `李 雷`（含空格） | Value error, 用户名只能包含中文、字母、数字、下划线，长度 3-32 位 |
| `玩家😀`（含表情） | 同上 |
| `小明!!`（含标点） | 同上 |

**注意**：前端已做同样的校验（3–32 个字符、支持中文/字母/数字/下划线、两次密码一致），
所以正常操作不会触发 422；若用 Postman/curl 测试则需自己满足约束。
`Content-Type` 必须是 `application/json`，漏了会得到 422 而不是 400。

### 2.6 `[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)`

**原因**：8000 已被别的进程占用（常见是上一次 uvicorn 没关干净）。

```bash
netstat -ano | findstr :8000
taskkill /PID <上面查到的PID> /F
```

或者直接换端口（两处都要改）：

```bash
python -m uvicorn main:app --host 127.0.0.1 --port 8010
```

```js
const API_BASE = 'http://127.0.0.1:8010';
```

### 2.7 保存记录返回"用户不存在"

**原因**：前端持有的 `user_id` 在 `users` 表里查不到。常见于：

- 清过库（`TRUNCATE users`）但浏览器仍保持上次登录态；
- 手工改过数据库；
- 用了另一个环境的 `user_id`。

**处理**：前端点「退出登录」重新登录即可拿到新的 `user_id`。
后端这层校验是刻意加的：比直接让外键报 1452 更友好。

### 2.8 保存记录报 `(1452, 'Cannot add or update a child row')`

**原因**：`game_records.user_id` 外键在 `users` 里找不到对应行，
且请求绕过了后端的"用户存在"预校验（例如直接写 SQL、或老版本代码）。

**处理**：

```sql
-- 查悬空记录
SELECT r.* FROM game_records r
LEFT JOIN users u ON r.user_id = u.user_id WHERE u.user_id IS NULL;

-- 清理（或补用户）
DELETE FROM game_records WHERE user_id NOT IN (SELECT user_id FROM users);
```

确认外键存在且是 `ON DELETE CASCADE`：

```sql
SHOW CREATE TABLE game_records\G
```

### 2.9 排行榜为空，但 `game_records` 里明显有数据

**原因**：`/get_rank` 用的是 **INNER JOIN**：

```sql
FROM game_records r JOIN users u ON r.user_id = u.user_id
```

只要 `user_id` 在 `users` 里不存在，这条记录就查不出来。

**处理**：同 §2.8，先修复悬空 `user_id`。

另有一种情况：`play_time` 为 `NULL` 时，后端 `r["play_time"].strftime(...)`
会抛 `AttributeError`，表现为 `/get_rank` 500。检查：

```sql
SELECT COUNT(*) FROM game_records WHERE play_time IS NULL;
UPDATE game_records SET play_time = NOW() WHERE play_time IS NULL;
```

### 2.10 中文用户名乱码（`??` 或 `å¤©`）

**原因**：字符集不是 `utf8mb4`，或连接未声明字符集。

**逐层检查**：

```sql
SHOW VARIABLES LIKE 'character_set_%';
SHOW CREATE TABLE users\G     -- 期望 DEFAULT CHARSET=utf8mb4
```

- 表建错了：`ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`
- 连接层：`db.py` 已显式传 `charset="utf8mb4"`（来自 `.env` 的 `DB_CHARSET`），不要删。
- 命令行查看时乱码可能只是控制台编码问题：`chcp 65001` 后再试。

### 2.11 `pip install` 报 429 Too Many Requests

**原因**：默认镜像限流（本项目搭建时遇到过）。

**处理**：换清华源或稍后重试：

```bash
python -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 2.12 改了 `main.py` 但行为没变

- 启动时没加 `--reload` → 手动 `Ctrl+C` 后重启。
- 加了 `--workers N` 时 `--reload` 无效，且多进程会缓存旧代码 → 重启整个命令。
- 浏览器缓存了旧 HTML → `Ctrl+F5` 强制刷新。

## 三、日志在哪看

| 日志 | 位置 | 关注点 |
|---|---|---|
| uvicorn 访问日志 | 启动终端窗口 | 每行 `POST /login 200`，可确认前端是否真的发出了请求 |
| uvicorn 异常栈 | 同上，`ERROR:` 开头 | 500 的真正原因在这里，不在前端提示里 |
| MySQL 错误日志 | `C:\ProgramData\MySQL\MySQL Server 8.0\Data\*.err` | 启动失败、崩溃、连接数打满 |
| 浏览器 Network | F12 → Network | 请求是否发出、状态码、响应体、CORS 报错 |
| 浏览器 Console | F12 → Console | `Failed to fetch`、JS 异常 |

**关键判断**：如果 uvicorn 终端**完全没有请求日志**，说明请求根本没到后端
（前端地址错 / 后端没起 / 被浏览器拦）；如果**有日志但状态码是 500**，
说明是后端代码或数据库的问题，直接看异常栈。

## 四、三条命令快速体检

```bash
# ① MySQL 活着吗
Get-Service MySQL80

# ② 库表在吗
mysql -uroot -p -D pinyin_war_game -e "SHOW TABLES; SELECT COUNT(*) AS users FROM users;"

# ③ 后端与数据库链路通吗
curl http://127.0.0.1:8000/health
```

三条都正常，问题基本就在前端（`API_BASE` / 浏览器缓存 / CORS）。

## 五、本项目已修复的坑（备查）

| # | 问题 | 处理 |
|---|---|---|
| 1 | bcrypt 5.x 导致注册 500（`__about__`） | 锁定 `bcrypt==4.0.1`，并在 `security.py` 加兼容补丁 |
| 2 | `pip` 安装被镜像限流 429 | 换清华源重装 |
| 3 | uvicorn 后台启动后日志文件为空、`/health` 无响应 | 确认进程真正存活：`netstat -ano \| findstr :8000`，再 `curl` 验证 |
| 4 | 前端只做了登录、结算没有上报成绩 | 结算页调用 `/save_game_record`，并新增排行榜页调用 `/get_rank` |
| 5 | 联调时游客也能提交成绩 | 前端判断 `currentUser`，游客只提示"成绩未上传" |
| 6 | 排行榜用户名可能含 HTML 特殊字符 | 前端渲染前做 `escapeHtml` 转义，防 XSS |
